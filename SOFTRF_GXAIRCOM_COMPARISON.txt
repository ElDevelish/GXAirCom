Critical Finding: INCOMPATIBLE PACKET STRUCTURES

Both implementations use identical physical layer parameters:
  ✓ Sync word: 0x55 0x99 0x95 0xA6 0x9A 0x65 0xA9 0x6A (8 bytes)
  ✓ Modulation: 2-GFSK, 100 kbps bitrate
  ✓ Frequencies: 868.2 MHz and 868.4 MHz
  ✓ Manchester encoding: Software-based (G.E. Thomas)
  ✓ Scrambling: 24-bit Galois LFSR with address seed

BUT they use INCOMPATIBLE PACKET STRUCTURES:
  ✗ GXAirCom:  27 bytes raw → 54 bytes Manchester-encoded
  ✗ SoftRF:    30 bytes raw → 60 bytes Manchester-encoded

  ✗ CRC Algorithm: GXAirCom uses 16-bit CRC-16/CCITT-FALSE
  ✗ CRC Algorithm: SoftRF uses 24-bit Hamming syndrome
  
  ✗ Packet Layout: Fields misaligned by 2-3 bytes
  ✗ Address Encoding: Different bit extraction methods


ROOT CAUSE OF TX/RX COUNTER PARADOX:

When radio receives counterparty's packet:
  1. Manchester demodulation SUCCEEDS → sync word found → counter increments ✓
  2. Packet structure parsing FAILS → fields misaligned → parse error ✗
  3. CRC validation FAILS → size/algorithm mismatch → packet rejected ✗
  4. Result: Counter shows communication, but payload never reaches app layer

Silent failure at packet validation level explains why counters increment
without any payload delivery.

WHEN GXAIRCOM TRANSMITS 54 BYTES (Manchester) AND SOFTRF RECEIVES:

Expected by SoftRF: 60 bytes (30 raw × 2 Manchester)
Actually received: 54 bytes (27 raw × 2 Manchester)
Difference: -6 bytes short

SoftRF's decode attempt:
  1. Finds sync word at expected position (happens to match)
  2. Reads 54 bytes (not 60)
  3. Tries to extract Length from offset [2] → reads GXAirCom's address byte
  4. Tries to extract Version from offset [3] → reads GXAirCom's Type field
  5. Tries to extract Address from [4-7] → reads GXAirCom's address + privacy + payload start
  6. Tries to extract Payload from [8-27] → reads corrupted data
  7. Tries to extract CRC24[3] from [28-30] → reads beyond packet bounds or gets wrong bytes
  8. CRC validation FAILS → Packet rejected


WHEN SOFTRF TRANSMITS 60 BYTES (MANCHESTER) AND GXAIRCOM RECEIVES:

Expected by GXAirCom: 54 bytes (27 raw × 2 Manchester)
Actually received: 60 bytes (30 raw × 2 Manchester)
Difference: +6 bytes extra

GXAirCom's decode attempt:
  1. Finds sync word (same as SoftRF's 0x55 0x99... at same position)
  2. Reads 60 bytes (expecting 54)
  3. Tries to extract Length from offset [0] → reads SoftRF's SYNC[0] (0x72 = 114 decimal, invalid)
  4. Tries to parse as 27-byte packet but has 30 bytes of data
  5. Tries to extract fields at wrong offsets
  6. Extracts CRC-16 from wrong bytes → CRC validation FAILS
  7. Packet rejected

3.1 CRC CONFIGURATION DIFFERENCES
────────────────────────────────────────────────────────────────────────────

                      GXAirCom              SoftRF
─────────────────────────────────────────────────────────────────────────────
CRC Type              CRC-16/CCITT-FALSE    24-bit Hamming Syndrome
CRC Polynomial        0x1021                Unknown (internal to RF.cpp)
CRC Initialization    0xFFFF                Hamming tables
CRC Size              16-bit (2 bytes)      24-bit (3 bytes)
CRC Bit Order         MSB first             Syndrome-based
CRC Coverage          25 bytes              27 bytes (more data)
Data covered          [0-24] of 27-byte     [0-26] of 30-byte
CRC Placement         Last 2 bytes          Last 3 bytes
Validation Method     Direct comparison     Syndrome check (should be 0)

CRITICAL ISSUE: CRC is LAST byte(s) of packet
- GXAirCom CRC at [25-26] in 27-byte packet
- SoftRF CRC at [28-29] in 30-byte packet
- When packets misaligned by 2 bytes, CRC bytes end up in WRONG positions
- This causes validation to fail for BOTH directions


3.2 GXAirCOM CRC IMPLEMENTATION
────────────────────────────────────────────────────────────────────────────

Function: adsl_crc16() [lib/ADSL/AdslProtocol.cpp L52-64]

  uint16_t adsl_crc16(const uint8_t *data, int len) {
    uint16_t crc = 0xFFFF;  // Init to 0xFFFF
    
    for (int i = 0; i < len; i++) {
      crc ^= (uint16_t)data[i] << 8;
      
      for (int b = 0; b < 8; b++) {
        if (crc & 0x8000u) {
          crc = (uint16_t)((crc << 1) ^ 0x1021u);  // Polynomial 0x1021
        } else {
          crc <<= 1;
        }
      }
    }
    return crc;
  }

Processing:
  - CRC covers first 25 bytes of 27-byte packet [0-24]
  - Result appended as bytes [25-26]
  - CRC calculated byte-by-byte with 8 iterations per byte (bit processing)
  - Polynomial 0x1021 applied when MSB is set
  - MSB-first processing order

Example: For GXAirCom packet:
  [0] Length
  [1-4] Net Header
  [5-9] Presentation Header
  [10-24] Payload (15 bytes)
  ────────────────── CRC starts at byte 0
  CRC processes bytes [0] through [24] = 25 bytes total
  Result stored in [25-26]


3.3 SOFTRF CRC IMPLEMENTATION
────────────────────────────────────────────────────────────────────────────

Implementation: Hamming/Syndrome-based (ads-l.h L511-530)

  static uint32_t checkPI(const uint8_t *Byte, uint8_t Bytes) {
    // Process Bytes of data (including 3 CRC bytes)
    // Calculate syndrome - should be ALL ZERO for valid packet
  }

  static uint32_t calcPI(const uint8_t *Byte, uint8_t Bytes) {

Processing:
  - CRC type defined as RF_CHECKSUM_TYPE_CRC_MODES (syndrome-based)
  - CRC covers 27 bytes of 30-byte packet [0-26]
  - Result is 24-bit Hamming code appended as bytes [28-29-30]  
  - Uses error-correcting code (not just error detection like CRC-16)
  - Syndrome calculation: computed on all 30 bytes, should equal zero


3.4 CRC MISMATCH CONSEQUENCES
────────────────────────────────────────────────────────────────────────────

When GXAirCom receives SoftRF packet (60 bytes, 30 raw):

  GXAirCom expects:
    - 27-byte packet
    - CRC at [25-26]
    - CRC covers bytes [0-24]
  
  Actually receives (mapped):
    - 30 bytes of SoftRF data
    - Tries to extract CRC from [25-26]
    - But [25-26] contains SoftRF payload bytes, not CRC!
    - SoftRF CRC is at [28-30] (3 bytes) which is beyond GXAirCom's 27-byte model
  
  Result:
    - CRC verification fails
    - Packet treated as corrupted
    - SILENT DISCARD (no error logged to user)


When SoftRF receives GXAirCom packet (54 bytes, 27 raw):

  SoftRF expects:
    - 30-byte packet
    - CRC at [28-30] (3 bytes)
    - CRC type: Hamming syndrome
  
  Actually receives (mapped):
    - 27 bytes of GXAirCom data
    - Tries to read CRC from [28-30]
    - But packet only has 27 bytes! Reads uninitialized buffer or zeros
    - CRC calculation on only 27 bytes with different algorithm
  
  Result:
    - Hamming syndrome check fails
    - Packet treated as corrupted
    - SILENT DISCARD


3.5 CRC SIZE IMPACT ON TRANSMISSION
────────────────────────────────────────────────────────────────────────────

GXAirCom transmission (54 Manchester bytes):
  27 raw bytes × 2 = 54 on-air bytes
  Last 4 bytes of Manchester stream encode 2 raw CRC bytes

SoftRF transmission (60 Manchester bytes):
  30 raw bytes × 2 = 60 on-air bytes
  Last 6 bytes of Manchester stream encode 3 raw CRC bytes

When decoding:
  - GXAirCom decodes last 4 bytes of Manchester → 2 raw CRC bytes
  - SoftRF decodes last 6 bytes of Manchester → 3 raw CRC bytes
  
Receiver misalignment:
  - If receiver has 54 bytes when expecting 60, last decoded bytes differ
  - If receiver has 60 bytes when expecting 54, has extra bytes after CRC
  - This breaks Manchester decode → decode error OR buffer overrun

SECTION 4: ADDRESS FIELD ENCODING DIFFERENCES
================================================================================

4.1 ADDRESS FIELD SIZE MISMATCH
────────────────────────────────────────────────────────────────────────────

GXAirCom Address:
  Size: 24-bit (3 bytes)
  Range: 0x000000 to 0xFFFFFF (0 to 16,777,215)
  Encoding: Direct binary representation
  Byte order: Little-endian (LSB first)
  Location in packet: Bytes [2-4] (Net Header) + bytes [6-8] (Pres Header)
    - Note: Address appears TWICE in packet!
    - Net Header: bytes [2-4]
    - Presentation Header: bytes [6-8] (with different interpretation)

SoftRF Address:
  Size: 30-bit (stored in 4 bytes with 2 unused bits)
  Range: 0x000000 to 0x3FFFFF (0 to 4,194,303) - note different max!
  Encoding: Shifted representation (>>6)
  Byte order: Complex packing in 4-byte Word[0]
  Extraction: (Value >> 6) & 0x00FFFFFF
  Location: Bytes [4-7] packed with Version field

CONSEQUENCE: Different address spaces!
  - GXAirCom can represent addresses 0 to 16,777,215
  - SoftRF can represent addresses 0 to 4,194,303
  - SoftRF's (>>6) shift means it uses only upper 24 bits of 30-bit field
  - Addresses with lower 6 bits set will be truncated in SoftRF


4.2 ADDRESS EXTRACTION CODE COMPARISON
────────────────────────────────────────────────────────────────────────────

Example address processing difference:

  Raw address value: 0x123456
  
  GXAirCom:
    Stores directly: 0x123456
    Uses as-is: 0x123456

    Stores shifted: 0x123456 << 6 = 0x48D1800 (if original intent)
    Extracts: (0x48D1800 >> 6) & 0xFFFFFF = 0x123456 (back to original)
    
  BUT: The shift happens at PACKING time, not extraction
  So if SoftRF packs with intent to send 0x123456:
    Packed as: 0x123456 << some_offset (unclear from code)

5.2 SCRAMBLING OFFSET CONSEQUENCE
────────────────────────────────────────────────────────────────────────────

When packets misaligned by 2 bytes:

GXAirCom TX scrambles:
  Bytes [5-24] using address seed
  These become on-air Manchester bytes [10-48] (approximately)

SoftRF RX attempts to descramble:
  Extracts its "bytes [5-24]" (which are actually GXAirCom bytes [7-26])
  Tries to descramble with extracted address (which is garbage due to offset)
  Result: DOUBLE CORRUPTION - offset + wrong seed = garbage payload

This is SECONDARY to packet structure mismatch, but compounds failure.

SECTION 6: TX/RX COUNTER INCREMENT MECHANISM
================================================================================

6.1 WHY COUNTERS INCREMENT DESPITE SILENT FAILURE
────────────────────────────────────────────────────────────────────────────

Event sequence in receiving radio:

1. RADIO LAYER (Successful):
   - Radio demodulates FSK signal
   - Manchester decoding finds sync word
   - Radio reports "packet received" to radio library
   → TX/RX Counter incremented HERE ✓

2. MAC LAYER (Attempted):
   - MAC layer attempts to extract Manchester-encoded bytes
   - Starts parsing packet structure
   - Reads version/length/CRC fields

3. PACKET VALIDATION LAYER (Failed):
   - CRC validation attempted
   - CRC size mismatch detected OR CRC value doesn't match
   - Packet marked as corrupted
   → Packet SILENTLY DISCARDED
   → No error generated to application
   → No data delivered

4. APPLICATION LAYER (Never reached):
   - Application never sees packet
   - Application counter would increment, but it never gets called
   - Only MAC-level counter was incremented


Code flow in GXAirCom [lib/FANETLORA/radio/fmac.cpp L284-350]:

3. Application layer attempts to parse packet structure
   → Field offsets all wrong due to packet size difference ✗

4. Application layer validates CRC
   → CRC size different (2B vs 3B) ✗
   → CRC algorithm different (CRC-16 vs Hamming) ✗
   → CRC offset wrong due to packet structure mismatch ✗
   → CRC validation fails 100% ✗

5. Application layer discards packet silently
   → No data delivered to user application
   → No error message generated
   → Only radio-level counter shows activity

RESULT: Perfect explanation for observed behavior
  - TX/RX counters show communication occurring
  - But no payload data received
  - No errors visible to user
  - Both directions fail identically

SECTION 11: RECOMMENDATIONS FOR RESOLUTION
================================================================================

To achieve interoperability, both implementations must align on:

1. PACKET STRUCTURE
   ─────────────────
   Option A: Adopt GXAirCom's 27-byte structure
     - Reduces air time
     - Simpler implementation
     - SoftRF would need to remove SYNC field and trim payload

   Option B: Adopt SoftRF's 30-byte structure
     - GXAirCom would add 2-byte SYNC prefix
     - Add extra CRC byte
     - Increase payload from 15 to 20 bytes

   RECOMMENDATION: Standardize on option that aligns with official SRD-860

2. CRC ALGORITHM
   ──────────────
   Option A: Keep GXAirCom's 16-bit CRC-16/CCITT-FALSE
     - Simpler computation
     - Standard algorithm
     - Error detection only

   Option B: Keep SoftRF's 24-bit Hamming Syndrome
     - Provides error correction capability
     - More robust against RF interference
     - More complex computation

   RECOMMENDATION: Standardize based on which better serves SRD-860 intent

3. ADDRESS FIELD
   ──────────────
   Option A: Direct 24-bit encoding (GXAirCom)
     - Simple, no shifting
     - Standard interpretation

   Option B: Shifted 30-bit encoding (SoftRF)
     - Supports 30-bit address space
     - Requires >>6 shift for extraction
     - Unusual for aircraft addressing

   RECOMMENDATION: Use direct 24-bit (matches aircraft ID standard)

4. PAYLOAD SIZE
   ─────────────
   Option A: 15 bytes (GXAirCom)
   Option B: 20 bytes (SoftRF)

   RECOMMENDATION: Standardize based on SRD-860 required fields

5. PROTOCOL IDENTIFICATION
   ──────────────────────────
   Both devices need a way to distinguish ADS-L packets from other protocols.
   
   Current issue: SoftRF has protocol detection logic, GXAirCom does not.
   
   RECOMMENDATION: Define identification bytes in sync pattern or packet header
   to enable dual-protocol reception on both platforms.
